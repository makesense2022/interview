# 技术负责人面试：这段项目该怎么讲（高分版本）

## 1) 60 秒电梯陈述（直接背）
- 背景：业务高速扩张，5 条业务线并行，多小程序协作，出现复制粘贴、无规范、交付慢的问题。
- 目标：统一架构与工程体系，提升复用与交付效率，降低包体与首屏。
- 方案：用 MVVM 抽象 UI/状态/模型边界；基于 pnpm workspace 的 monorepo 统一依赖与构建；MobX 管理跨页面状态；建设共享组件库与通用模型层；引入 MCP（AI 工具上下文注入）提升研发效能。
- 结果：复用率 +80%，交付周期 -40%，协作效率 +60%，构建时长 -50%，包体 -30%，首屏 -25%，支撑 5 个业务线稳定发布。

## 2) 3–5 分钟结构化叙述（SPQA/STAR 框架）
- 问题 P（Problem）
  - 多小程序并行但无统一模块边界与规范；复制粘贴引起 Bug 回归；发布链路冗长；依赖漂移导致线上事故。
- 目标 Q（Goal/Success Metrics）
  - 架构统一、复用提升、交付加速、稳定可回滚。明确指标：复用率、开发周期、构建时长、包体与首屏、协作效率。
- 方案 A（Approach）
  - 架构层：MVVM
    - View 仅渲染；ViewModel 承担状态与副作用；Model 抽象后端契约与缓存策略。
    - 数据流：API -> Model（缓存/映射）-> ViewModel（可观察状态）-> View（渲染/绑定）。
  - 工程层：monorepo（pnpm workspaces）
    - 包划分：apps/*（各小程序）、packages/ui（组件库）、packages/models（通用模型层）、packages/utils、packages/config。
    - 统一 TS 配置与 Project References，保证类型跨包增量编译；依赖锁与统一构建脚本。
  - 状态层：MobX
    - 以 store 切功能域；使用 computed/autorun 降低手写 setData；对异步副作用 standardize（如 flow 或封装 action）。
  - 复用层：组件库 + 通用模型层
    - 组件库抽象跨小程序可复用 UI 能力（主题/样式隔离/平台差异）；模型层沉淀接口与缓存，避免重复接入。
  - 效能层：MCP + AI 上下文注入
    - 将组件库/模型层的 API 文档与类型注册到 AI 工具上下文，提升自动补全与生成代码的正确率。
  - 流程层：规范与 CI/CD
    - 代码规范（lint/commitlint/branch 约定）、变更集发布（changeset）、受影响图增量构建、预发灰度、回滚开关。
- 结果 R（Result）
  - 指标达成（用数字与对比图说话）；线上事故减少；团队满意度与协作效率显著提升；新同学上手更快。

## 3) 白板/口述架构图要点（如何画）
- 顶层：apps/miniapp-a … miniapp-e ──依赖── packages/ui、packages/models、packages/utils
- 横切：pnpm workspace + TS refs + 统一构建脚本（build、dev、test、release）
- MVVM：View <-> ViewModel（MobX observable/computed/action）<-> Model（API/缓存/映射）
- 数据流：API -> Model 缓存（LRU/stale-while-revalidate）-> VM -> setData(render)
- DevOps：CI 检测受影响图 -> 只构建受影响包 -> e2e/contract test -> 分环境部署 -> 回滚策略
- AI 工具：MCP 注入组件/模型 API 语义，辅助代码生成与重构

## 4) 关键技术取舍与“为什么”
- 为什么 MVVM（在小程序场景）：
  - setData 成本高，直接操作会散落；MVVM 让“状态→视图”可预测，降低手写绑定复杂度。
- 为什么选择 MobX 而不是 Vuex/Redux：
  - 小程序/多端 DSL 适配，MobX 响应式成本低、心智负担小、代码量少；可逐步落地，不强制全局不可变。
- 为什么 monorepo + pnpm：
  - 强锁与去重，提升构建速度；跨包引用天然一致；配合 TS Project References 得到增量编译与 IDE 友好。
- 为什么组件库 + 模型层分离：
  - UI 和业务契约解耦；组件库复用“长尾 UI 能力”；模型层统一容错/重试/缓存策略，避免接口风格漂移。
- 为什么 MCP：
  - 将私有库上下文暴露给 AI，减少幻觉与误用；在重构与脚手架生成上显著提效。

## 7) 可预期追问与短答
- Q1：为什么不是微前端/模块联邦（MF）？
  - 多小程序天然隔离，交互少；重用集中在“组件与模型层”，MF 的远程依赖协商收益不如 monorepo 的一致性与速度。若未来出现跨应用路由拼装/独立发布诉求，再引入 MF 或者 runtime remote 均可。
- Q2：团队治理怎么落地？
  - 规范模板化（eslint/prettier/stylelint/commitlint）；PR 模版 + ADR（架构决策记录）；强制 check（CI）；代码所有权与 reviewers 列表；指标看板落地。
- Q3：如何保障稳定性与回滚？
  - feature flag + 灰度；每包独立版本与回滚脚本；模型层降级策略（兜底数据/本地缓存）；静态资源回滚与监控报警闭环。
- Q4：如何处理包体与首屏？
  - 路由分包、按需注入；资源压缩；图片策略（WebP/AVIF）；预加载关键模型；骨架屏与延迟加载。
- Q5：如何跨小程序复用？
  - 把差异聚焦在适配层；UI 组件库与模型层保持平台无关接口；通过 workspace 复用与版本门禁。
